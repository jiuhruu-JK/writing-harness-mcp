## 目标

让不同写作 Agent 通过同一个 MCP，在同一项目文件夹中按13阶段接力；共享权威稿件版本、人工裁决与分层记忆；角色只获得自己的工具、提示词与上下文；冲突不覆盖、过程可追溯、错误可回滚。

MVP 交付冷启动人工协同和全部接口契约。MCP不内置写作、审核、embedding或TTS模型。生产向量后端、自动模式、自动记忆维护不在MVP内。

## 范围

### MVP内

- 单项目数据根、SQLite权威状态、不可变内容快照、可读镜像。
- 13阶段状态机、串行与并行规则、人类锁、精确版本人工批准、回滚和审计。
- 七个AI角色各自独立的 assignment、submission、context、prompt 四个叶子模块。
- 人类与外部工具提交、项目记忆、人工晋升总记忆、外部修辞导入。
- stdio与Streamable HTTP共用工具注册表。
- 向量全部叶子模块的接口契约、兼容性矩阵、固定测试夹具与符合性测试；后端未接入时明确报 `VECTOR_BACKEND_UNAVAILABLE`。

### MVP外

- 生产向量索引、自动小爽点、自动疲劳裁决、自动记忆整理、跨用户学习。
- Web/GUI、TS前端、编辑器插件、远程多租户、计费与托管服务。
- 模型运行时、模型密钥管理、自动调度平台。
- 双语言长期并行实现。

## 最小模块判定

- 一个叶子模块一个文件夹、一个 `run(payload: dict) -> dict`、一套同步测试、一张任务卡。
- 一个模块只承担一个可独立改变、独立验收的职责。
- 分类目录不是业务包；不得建立总 `contracts`、`store`、`workflow`、`memory`、`mcp_api`、`review`、`prompt` 业务模块。
- 改某个角色提示词不得改工具schema；改切分不得改检索；改小爽点不得碰疲劳。
- 纯内部helper留在使用模块内部，不单列伪模块。

叶子模块清单以 [interface总表](2026-11-01-writing-harness-mcp.interfaces.md) 为单一事实源；任务卡与对话批次必须与它逐字一致。

## 要求

### 要求 R1：项目与数据隔离

- 要求陈述：服务实例必须绑定单一项目数据根，所有数据库查询和文件访问必须强制带当前项目作用域。
- 场景 项目根：当打开一个项目时，则返回稳定的 `project_id`、schema版本与数据根状态；同一数据根不能登记为两个项目。
- 场景 路径逃逸：当读取路径包含目录穿越或跳到根外符号链接时，则拒绝并返回 `PROJECT_SCOPE_VIOLATION`。
- 场景 跨项目查询：当请求其他项目记录时，则默认不可见，不得以向量检索或文件路径绕过。

### 要求 R2：不可变内容与精确读取

- 要求陈述：任何稿件、大纲、事实账本、外部范本、媒体登记都必须形成带哈希的不可变版本。
- 场景 新版本：当提交内容时，则快照先落盘，再事务提交元数据；崩溃不得留下指向不存在内容的当前指针。
- 场景 历史读取：当请求历史版本时，则返回该版本原始字节，不随当前文件更新。
- 场景 哈希或版本不符：当读取指定的 version/hash 不匹配时，则拒绝，不得回退到最新版本。

### 要求 R3：版本治理与回滚

- 要求陈述：系统必须提供 diff、血缘、审计事件和回滚，且回滚不删除历史。
- 场景 回滚：当人基于历史版本回滚时，则创建新版本，旧版本和事件保留，受影响批准失效，下游标 stale。
- 场景 血缘：当查询某个输出时，则能追溯输入版本、候选、范本、prompt版本和上下文manifest。
- 场景 归档：当版本不再为当前版本时，则默认检索排除，但显式历史查询仍可读取。

### 要求 R4：13阶段与人工控制点

- 要求陈述：状态机必须显式覆盖13阶段；非法跳转、错误角色和未满足人工批准点的推进必须拒绝。
- 场景 非法推进：当跳过阶段或由AI执行人类阶段时，则拒绝并保持原状态。
- 场景 精确批准：当批准的目标版本或哈希变化后继续推进时，则拒绝并返回 `HUMAN_DECISION_REQUIRED`。
- 场景 人类锁：当锁生效时，则AI begin/submit被拒绝，读取可用；断线或重启不自动解锁。

### 要求 R5：串行与并行

- 要求陈述：逻辑审核按片串行；文风候选可并行但只能写侧支；候选批次关闭后逻辑校正串行写回主线。
- 场景 串行冲突：当两个逻辑审核同时取得主线租约时，则只有一个成功，另一个得到冲突错误。
- 场景 并行候选：当多个文风候选同时运行时，则各自只写自己的侧支，主线head不变。
- 场景 校正：当候选批次关闭后校正时，则读取固定候选与当前正典，只产生一个主线版本，并保留采用、驳回和冲突校正记录。

### 要求 R6：小爽点与审美疲劳独立

- 要求陈述：小爽点与审美疲劳必须具有独立阶段、角色、工具、上下文和提示词，不得共用一个review模块或提示词。
- 场景 上下文隔离：当小爽点角色连接时，则看不到疲劳提示词和历史；疲劳角色同样看不到小爽点提示词。
- 场景 顺序：当小爽点阶段未完成时，则不能推进到疲劳阶段。
- 场景 未来自动化：当自动模式未实现时，则必须显式报告不可用，不得静默执行假自动。

### 要求 R7：角色工具与提示词隔离

- 要求陈述：七个AI角色必须各自拥有 assignment tool、submission tool、context、prompt 四个叶子模块；共享的只有传输、会话路由、公共envelope和工作底层能力。
- 场景 发现：当会话绑定某角色时，则只发现该角色的工具与提示词。
- 场景 成本：当取任务时，则只返回当前提示词版本、任务、输出schema、最小上下文和预算；不返回全部历史或其他角色中间产物。
- 场景 变更隔离：当修改一个角色提示词时，则其他角色的文件、schema和测试快照零变化。

### 要求 R8：项目记忆与总记忆

- 要求陈述：原始日志、项目记忆、跨项目总记忆、外部修辞库必须分层并强制作用域。
- 场景 原始日志：当日志尚未整理和人工确认时，则默认检索不可见。
- 场景 项目隔离：当检索项目记忆时，则不能返回其他项目内容。
- 场景 人工晋升：当无人工晋升记录时，则不能把项目记忆写入总记忆；晋升记录必须保留原项目和原版本血缘。
- 场景 修辞来源：当导入作者定稿为外部修辞时，则拒绝；外部范本必须带来源与许可信息。

### 要求 R9：向量来源与预切分

- 要求陈述：进入向量管线的内容必须绑定精确 `SourceRef`，归一化、切分、稳定chunk_id和原文offset映射必须可复现。
- 场景 来源绑定：当源版本或哈希不符时，则拒绝建立索引。
- 场景 原文回溯：当给定任意chunk时，则能映射到指定 source_version＋source_hash 的精确UTF-8字节范围。
- 场景 重建稳定：当使用相同来源、配置和边界重建时，则chunk_id完全一致；配置变化时不得复用旧chunk_id。
- 场景 切分边界：当存在章节、场景、段落和句子边界时，则优先按结构切分；只有超长时才按版本化降级规则切分。

### 要求 R10：向量配置对齐

- 要求陈述：文档、索引和查询必须使用兼容的 normalizer、chunk_profile、embedding_profile、distance、dimension 与 index_profile。
- 场景 不兼容：当维度相同但模型revision、归一化或distance不同的时候，则必须在检索前拒绝。
- 场景 外部向量：当向量维度不符、数值非有限或范数不符合配置时，则拒绝入库。
- 场景 查询模式：当短查询进入检索时，则按查询模板直接归一化和嵌入，不机械使用文档语义chunker，不生成文档offset_map。

### 要求 R11：检索、排序与材料化

- 要求陈述：检索必须按固定顺序执行配置检查、作用域过滤、当前版本过滤、候选召回、阈值、确定排序、去重、top_k、有界父子扩展和精确原文物化。
- 场景 候选数：当 `candidate_k < top_k` 时，则拒绝。
- 场景 跨项目：当检索返回前，则必须完成作用域过滤；跨项目污染为零。
- 场景 历史：当查询历史版本时，则显式标记 `historical=true`；默认不得返回过期版本。
- 场景 物化：当返回引用时，则必须使用chunk绑定的source version/hash，不得偷换成最新稿。

### 要求 R12：向量治理与质量

- 要求陈述：索引重建、删除和质量评估必须有独立模块、代际切换和审计。
- 场景 重建：当新索引构建时，则旧代际继续只读，校验通过后原子切换。
- 场景 删除：当删除数据时，则幂等删除向量、元数据、父子关系并留tombstone，旧任务不能复活数据。
- 场景 质量：当运行固定golden集时，则记录Recall@10、原文准确率、项目污染、过期版本污染和配置拒绝结果。

### 要求 R13：传输与协议

- 要求陈述：stdio与Streamable HTTP必须共用同一业务核心、工具schema、错误码和契约测试。
- 场景 双传输：当同一契约套件在两种传输运行时，则领域语义一致。
- 场景 断线：当客户端断线重连时，则不会自动提交或转移写作租约。
- 场景 协议后端：当官方SDK未实现某客户端特性时，则报告明确不支持，不作虚假兼容承诺。

### 要求 R14：可靠提交与恢复

- 要求陈述：提交必须使用幂等键、base revision/hash、写入租约和内容哈希；崩溃恢复不得覆盖第三方修改。
- 场景 重试：当同actor、同幂等键、同请求重试时，则返回首次结果；同键不同内容则拒绝。
- 场景 过期提交：当租约过期或fencing token过旧时，则拒绝，要求重新取租约和新base。
- 场景 崩溃：当数据库已提交但镜像未同步时，则按journal补齐；发现第三方哈希时停止自动修复并生成冲突。
- 场景 外部编辑：当用户直接修改可读镜像后，则普通提交被阻止，必须显式导入并处理冲突。

### 要求 R15：开源自托管与可迁移

- 要求陈述：公开契约、SQL migration、文件格式和事件语义必须语言中立；未来Rust服务端可复用同一数据和MCP契约。
- 场景 无私有协议：当实现MCP时，则使用官方SDK和标准JSON-RPC语义，不增加只对Python开放的必需字段。
- 场景 数据可携带：当复制项目数据根时，则稿件快照、状态、事件和项目记忆可被另一实例打开。

## 接口

所有叶子模块统一入口：

```text
接口：run(payload: dict) -> dict
├── 入参：request_id: str（调用方生成的请求标识）
├── 入参：project_id: str（项目作用域）
├── 入参：actor: dict（actor_id、role、client_instance_id）
├── 入参：idempotency_key: str（所有写操作必填）
├── 入参：payload 的业务字段见接口总表
├── 返回：ok: bool
├── 返回：data: dict（成功结果）
├── 返回：error: {code, message, details}
└── 错误：模块专属异常，统一映射为稳定错误码
```

- 每个叶子模块拥有一个独立异常类，命名 `<ModulePascal>Error`。
- 写模块必须在同一SQLite事务内校验幂等键和业务约束。
- 稳定错误码至少包括：`CONFLICT`、`STALE_BASE`、`LEASE_EXPIRED`、`STALE_FENCING_TOKEN`、`HUMAN_LOCKED`、`HUMAN_DECISION_REQUIRED`、`IDEMPOTENCY_KEY_REUSE`、`PROJECT_SCOPE_VIOLATION`、`EXTERNAL_EDIT_CONFLICT`、`VECTOR_PROFILE_MISMATCH`、`VECTOR_BACKEND_UNAVAILABLE`。
- 每个模块的精确入参、返回和错误见 [接口总表](2026-11-01-writing-harness-mcp.interfaces.md)；修改接口先改总表再改任务卡。

## 必须禁止

- 不把七个角色塞进一个共享review工具或共享prompt。
- 不把大爽点或最终审美交给AI裁决。
- 不把作者定稿导入外部修辞库。
- 不让默认检索读取原始日志、未确认候选或其他项目记忆。
- 不把维度相同当作向量配置兼容。
- 不用当前最新稿替代chunk绑定的历史原文。
- 不让MCP session代替写作租约或人工锁。

## 验收

详细接口和向量测试以两份规范附件为准：

- [接口总表](2026-11-01-writing-harness-mcp.interfaces.md)

总体验收必须通过：

1. A客户端退出后，B以不同角色取得同一head和各自最小上下文并继续。
2. 七个角色工具/提示词隔离测试通过，修改一个prompt不影响其他模块。
3. ③串行、④候选批次关闭后串行校正、⑤与⑥独立的状态测试通过。
4. 幂等、过期提交、崩溃恢复、外部编辑冲突、人类锁和精确版本批准测试通过。
5. 项目隔离、原始日志不可检索、人工晋升和修辞来源约束测试通过。
6. 向量契约、配置拒绝、SourceRef/ContextItem和golden fixture测试通过；无后端时报明确不可用。
7. stdio与HTTP跑同一契约套件；真实客户端只在实测后登记。
